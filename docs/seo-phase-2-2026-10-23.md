# Corrección SEO, fase 2 — dominio Vercel duplicado — 23/10/2026

Estado: cambio local en `main`, con commit local y sin push ni despliegue. No se
modificó Vercel, DNS, variables de entorno, la API, la base de datos ni
integraciones externas. Las consultas a producción fueron `GET` de solo lectura.

## Problema

`https://mymacademia-platform.vercel.app/` responde 200 con el mismo contenido
público que `https://www.mymacademiadebaile.com.ar/`. Desde la fase 1 declara
canonical hacia www, pero el canonical es una sugerencia: Google sigue
encontrando e indexando URLs del alias.

## Dependencias reales del dominio Vercel

`vercel.json` define un solo proyecto con Services: `/api/*` va a Express y el
resto a Next. Por lo tanto **el alias Vercel sirve la web y la API completas**,
igual que www.

| Dependencia | Evidencia | Usa vercel.app | Clasificación |
| --- | --- | --- | --- |
| `APP_ORIGIN` (CORS, enlaces de recuperación, logo de correos) | Header público `Access-Control-Allow-Origin` de `/api/health` en ambos hosts: `https://mymacademiadebaile.com.ar` (apex sin www) | No | Independiente del alias |
| Recuperación de contraseña | `auth.routes.ts` arma el enlace con `APP_ORIGIN`; apex responde 308 a www conservando el token | No | Independiente |
| Login, renovación y logout | Cookies `mym_access`/`mym_refresh` host-only, `/api` same-origin | Solo para sesiones abiertas en el alias | Operativa por host; no se mueve |
| Backoffice `/admin/*`, portal `/professor/*`, `/check-in` | Rutas Next privadas que llaman a `/api` del mismo host | Solo si el personal entra por el alias | Operativa por host; no se mueve |
| API, finanzas, tareas `/api/internal/*` | Express detrás de `/api/*`; consumidores externos sin inventario en el repo | Desconocido fuera del repo | No se toca |
| Webhooks y callbacks OAuth | No hay implementaciones entrantes en el repo | No | Sin dependencia conocida |
| SSR → API | Binding privado `API_INTERNAL_URL` | No | Independiente |
| PWA docente | `manifest.ts`, `start_url: /professor` | Solo instalaciones hechas desde el alias | No se mueve |
| SEO (canonical, OG, sitemap, robots, JSON-LD) | Origen fijo www desde la fase 1 | No | Ya corregido |
| Literal `mymacademia-platform.vercel.app` en el código | Solo en tests y documentación | No | Sin dependencia |

No se pudo inspeccionar el proyecto Vercel, cron jobs externos, marcadores del
personal ni analíticas por host. Cualquier uso del alias para trabajar se limita
a rutas que esta fase **no redirige**.

### Hallazgo fuera de alcance: kiosco de asistencias y `APP_ORIGIN`

`check-in.routes.ts` rechaza con 403 `INVALID_ORIGIN` todo request no-GET cuyo
`Origin` difiera de `APP_ORIGIN`. En producción `APP_ORIGIN` es el apex, pero el
apex redirige a www, así que el navegador del kiosco envía
`Origin: https://www.mymacademiadebaile.com.ar`. El módulo está desplegado
(`GET /api/check-in/device` responde 401 `DEVICE_NOT_AUTHORIZED`). Por inferencia,
la activación y el registro de asistencias por QR se rechazarían tanto en www
como en el alias. No se envió ningún POST a producción para confirmarlo.

Solución probable, que requiere autorización: cambiar `APP_ORIGIN` en Vercel a
`https://www.mymacademiadebaile.com.ar` y redeplegar. Los enlaces de recuperación
y el logo de correos pasarían a www sin el salto 308; CORS sigue siendo
same-origin en producción. Verificar antes con el personal si el kiosco funciona
hoy. Este cambio no forma parte de esta fase.

## Alternativas evaluadas

| Opción | Resultado SEO | Riesgo operativo |
| --- | --- | --- |
| A. 308 de todo el dominio Vercel | Máximo | Alto: mueve `/api/*`, cierra sesiones host-only, rompe PWA instaladas y cualquier consumidor externo; un POST redirigido a otro origen exige CORS y cookies que www no tiene para ese cliente |
| B. 308 solo de páginas públicas | Máximo para las URLs indexables: consolida señales y lleva visitantes a www | Bajo: las páginas públicas no tienen sesión, formularios ni Server Actions |
| C. `X-Robots-Tag: noindex` por host | Desindexa, pero no consolida señales; canonical y noindex se contradicen en las URLs públicas | Nulo |

**Elegida: B para el alias de producción + C para todos los demás hosts no
oficiales.** Las páginas públicas del alias redirigen; el resto de respuestas del
alias (login, backoffice, kiosco, sitemap, robots, assets), las URLs de preview,
las URLs únicas de deployment y cualquier otro host reciben `noindex`. www no
cambia. `robots.txt` sigue permitiendo el rastreo en todos los hosts para que
Google pueda ver las redirecciones y el header.

Los previews no se redirigen: dejarían de servir para revisar cambios públicos.
Las URLs únicas de deployment de producción tampoco: no se distinguen de las de
preview por el host, y con `noindex` alcanza.

## Implementación

Reglas declarativas en `next.config.ts`; sin proxy ni código en runtime. Next las
compila en `routes-manifest.json` y Vercel las aplica en su capa de routing.

- `redirects()`: `/`, `/clases`, `/clases/:slug`, `/horarios`, `/contacto`,
  `/profesores`, `/profesores/:slug`, solo con `host` exacto
  `mymacademia-platform.vercel.app`, 308 a la misma ruta en www. Next conserva el
  query string (`utm_*`, `fbclid`).
- `headers()`: `X-Robots-Tag: noindex` en `/:path*` cuando el host **no** es
  `www.mymacademiadebaile.com.ar`.
- `/api/*` no llega a Next en Vercel (lo enruta `vercel.json` a Express), así que
  ninguna regla puede afectar API, auth, finanzas, check-in ni tareas internas.
- La caché CDN de Vercel incluye el host en la clave, por lo que una respuesta
  con `noindex` del alias no puede servirse en www.

El fragmento inactivo `docs/examples/seo-public-redirects.vercel.fragment.json`
de la fase 1 queda reemplazado por estas reglas y no debe activarse.

### Páginas 404

Antes, `/clases/<inexistente>` y `/profesores/<inexistente>` respondían 404 pero
heredaban del layout público canonical y `og:url` a la home, `index, follow` y
el título de la home. `/<inexistente>` tenía título genérico.

Ahora todas las 404 usan `NOT_FOUND_METADATA`: título
`Página no encontrada | M&M Academia de Baile`, sin canonical ni Open Graph,
`noindex, nofollow`. El 404 sigue siendo 404.

### lastmod del sitemap

No se agregó. La proyección pública de la API no expone fechas y el `updatedAt`
de Mongoose cambia con modificaciones no editoriales. Incorporarlo exigiría
cambiar la API y definir qué cuenta como cambio de contenido.

Los e2e por host fijan el header `Host` contra `next start`:

- Alias: `GET`, `HEAD` y `POST` a cada página pública responden 308 a la misma
  URL en www (308 preserva método y cuerpo). El query string se conserva.
- Alias: `/login`, `/forgot-password`, `/reset-password?token=…`, `/admin`,
  `/admin/payments`, `/professor`, `/check-in`, `robots.txt`, `sitemap.xml` y el
  logo responden 200 sin redirección y con `X-Robots-Tag: noindex`.
  `GET`/`POST /api/auth/refresh` no reciben 308.
- www: todas las páginas públicas 200, sin `X-Robots-Tag`.
- Preview y URL única de deployment: 200 con `noindex`, sin redirección.

Límite: las pruebas locales ejecutan las reglas en el servidor de Next. En Vercel
las aplica la capa de routing a partir del mismo manifest; hay que verificarlo
después del despliegue.

## Rollback

- Rápido: en Vercel, "Instant Rollback" al deployment anterior. Las reglas viven
  en el build, así que no queda nada activo.
- Código: `git revert <commit>` y nuevo deploy.
- Los 308 pueden quedar cacheados en navegadores que ya los recibieron. Solo
  afecta a páginas públicas, que funcionan igual en www.
